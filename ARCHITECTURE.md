# ARCHITECTURE (condensed, 1 page)

> Scope: 1-page arch summary for agents. Full spec: `Documentation/1.Architecture.md`.
> Status: Active | Date: 2026-11-01

- **Request path:** Browser → Nginx (`storefront./admin./api.` domains) → Next.js apps (:3000/:3001) or NestJS service by `/api/<route>` prefix → Postgres/Mongo/Redis.
- **Event path:** producers never publish from a request handler: all five write an outbox row in the same transaction as the domain change (auth/cart/catalog/order → Postgres `<schema>.outbox`; cms → Mongo `cms_outbox`), and a relay from the shared **`@ecom/messaging` 0.5.0** package claims them — Postgres with `FOR UPDATE SKIP LOCKED` under one session advisory lock per schema, Mongo with repeated atomic `findOneAndUpdate` under a `<collection>_locks` lease document — publishes sequentially keyed by aggregate id, and marks them published; retry backs off on `locked_until` and parks at `failed` after five attempts. One `OutboxStorePort<Ctx>` has two implementations, so there is one relay and one retry policy for both databases. Consumers are `@EventPattern` routes on the **Nest Kafka transport** (`@nestjs/microservices`) built by the same package: one strategy and one group per service, the group named exactly the service (`postfixId: ''`), several topics as routes on that single strategy, `KafkaEventHandler.run` owning parse → retry ladder → dead letter → counter → manual commit in that order, `ProcessedEventsStore` claiming the event id in the caller's transaction. Self-hosted KRaft in every environment — no env switch and no SNS adapter; topics + `.dlq` twins + replay. `ITaskQueue` (`SqsTaskQueue`) carries jobs only — `notify-send-email`, `import-process-row`, `media-resize-image`. `cms.updated` has **no** Kafka consumer: invalidation is **HTTP**, cms-svc calling the storefront's `POST /api/revalidate` with a shared secret (`x-revalidate-secret` + `{"tags":[…]}` → `revalidateTag(tag,'max')`), never Kafka — the arrow exists and is tested as of `sf-050`, and `cms-007` is the caller that does not exist yet. Storefront/admin hold no broker credentials: page views go `Next /api/track` → `analytics-svc` → Kafka. Envelope identical everywhere; money is a **number** on every wire (ADR 41/42: producers normalise `DECIMAL` at their own DB boundary and contracts 1.10.0 narrowed `refundAmount` to match). Contracts pins: **1.10.0 order-svc**, **1.9.0** on catalog and search (the two `product.imported` consumers) and ecom-messaging (devDep), 1.8.0 elsewhere except the storefront at 1.7.0.
- **Consumer path (§6.5, ADR 34-40):** three consumers, one protocol, and the differences are only the handler each service contributes. **cart** consumes `order.created` and converts the cart idempotently — the `processed_events` claim and the `UPDATE … status='converted'` + `cart.outbox` write commit or roll back together, and a shopper with no active cart is `ignored` rather than dead-lettered; the Phase-0 HTTP convert route is deleted, so checkout no longer calls cart at all (`ord-012` is the leftover `CartClient` in order-svc, which already treats `404` as non-fatal). **catalog** consumes `order.created` (reservation commit, untouched by `cat-008`) and `product.imported` on one strategy: it upserts product/category/brand/variants/images, writes imported stock as **physical minus open holds** (`onHand = max(0, imported − openReserved)`) plus one `stock_movements` row `reason='import'`, and **re-emits nothing** — search already subscribes to `product.imported`, so a 10k-row import must not become 10k events. **search** consumes `product.updated`, `category.updated`, `blog.updated`, `product.imported` with zero business-logic change, which is what proved the module. DLQ reasons are the package's four plus each service's own (`unresolved-reference`, `sku-conflict`, `slug-conflict`, `variant-sku-conflict` in catalog). A failed DLQ write is the only case that throws (`KafkaConsumerStalledError`) and it stops the consumer rather than committing past a lost record.
- **Data:** DB-per-service, FKs only inside own schema; cross-service refs = logical UUID. Four Postgres outbox tables (`auth`, `cart`, `catalog`, `order` — the last one now an envelope table with `envelope`/`locked_until`/`last_error` and a nullable legacy `payload`) plus the Mongo `cms_outbox` collection; idempotency keys everywhere; saga-lite compensation on stock fail.
- **Producer outbox (§6.5, ADR 21-26):** the store quotes its identifiers (`"order"."outbox"` — `order` is a reserved word), validates the envelope and payload before the insert, and the relay is the only thing that publishes. There is no in-process producer bus left: catalog's `KafkaEventBus` and cms's `cms.events` publish are deleted, and `media.tasks` is the one publish still on the direct path until `cms-006` moves it to SQS. CMS invalidates its Redis cache **after** the Mongo transaction commits, never inside it.
- **Frontend:** Server Components fetch + `lib/cms/resolve.ts` (P>S>G) → dumb props; smart state only in route islands + `store/`.
- **Storefront seams (HTTP only, `sf-049`/`sf-050`/`sf-051`):** three arrows out of the UI, all HTTP. **Auth** — four BFF handlers (`app/api/auth/{login,register,refresh,logout}`) call auth-svc and own the `HttpOnly` cookies (`sf_at` 15m at `Path=/`, `sf_rt` 30d at `Path=/api/auth`; `Secure` in production), answering only `{user}`/`{ok:true}` so no token ever reaches client JS; `proxy.ts` forwards exactly one path, `GET /api/auth/session` → auth-svc `/me`, injecting the `Authorization` header server-side and stripping the inbound cookie, and guards `/account/*` + `/checkout/*`. **CMS** — every read is `fetch(…, { next: { tags: [cmsTag], revalidate: 300 } })` via `lib/cms/{client,tags,navigation,pageSettings}.ts`, so the Next Data Cache is the shared layer and the tag is the purge handle; `fetchNavSettings` cascades `cms-svc → a bounded 32-entry in-process TTL cache → DEMO_NAV_INPUT` and the root layout has no throwing path, so a cms-svc restart degrades the nav instead of blanking every route; `POST /api/revalidate` is secret-gated (constant-time over the SHA-256 of both sides, fails closed when `REVALIDATE_SECRET` is unset) and rejects any tag outside the shared vocabulary. **Commerce (sf-051, full spec `Documentation/1.Architecture.md` §6.7)** — one registry (`lib/services/urls.ts`) and two transports (`lib/http/{result,client,browser}.ts`): a server-only client (timeout, envelope parse, zod check, never throws — every failure is a `ServiceResult` `kind`) and the browser's `bff()` (same-origin, `x-idempotency-key` minted once per logical mutation, single-flight 401 refresh, one replay). Catalog is read in RSC with `revalidate: 60` and `status:"active"` fixed in the client; cart/checkout/account are client-rendered private data behind `no-store` BFF handlers; the guest cart id `sf_cid` is minted by the proxy, merged **server-side** inside login/register and rotated after success; `/api/account` fans out with per-section degradation. Money is a plain number end to end — the consumer-side normalizer was deleted when order-svc began parsing `DECIMAL` at its own DB boundary (ADR 41/42).
- **Deploy:** per-repo image → GHCR, `ecom-infra/VERSIONS.env` pins tags; one service at a time; rollback = revert one line. Health `/health` + `/health/ready`, `x-request-id` tracing, CloudWatch alarms.
