| 13 | Idempotency authority | 2026-10-29 | The **domain row is the authority**: the key is persisted on the record it protects (`order.orders` + partial unique index on `(user_id, idempotency_key) WHERE idempotency_key IS NOT NULL`); Redis (`idem:{userId}:{route}:{key}`) only caches the response for replay | A bare `idem:{key}` let one user's retry replay another user's confirmation; and a crash between `COMMIT` and `REDIS SET` duplicated the order because the cache was the only record. The unique index also *is* the concurrency gate: the loser of a race gets `23505`, not a second order | Redis as the only idempotency record; global unscoped keys; a separate `idempotency_keys` table detached from the row |
| 14 | Payment saga | 2026-10-29 | Persist the order as `pending` (TX1: order + items + history + `payments.status='pending'`) **before** capture, capture against the real `orderId`, then confirm in TX2. Every post-capture failure is compensated (provider refund of its own capture, `releaseStock` once), and a retry of a `pending` key **resumes** the saga instead of starting a new one | Capturing money before the row existed (`'order-temp'`) meant a DB failure took the payment and left nothing behind to reconcile, and there was no state in which a crash could be detected. Pending-first makes the write the first durable act and keeps the hold ahead of it | Capture-then-persist; a distributed lock spanning the whole saga; log-and-continue on failed money movement |
| 15 | Refunds | 2026-10-29 | A `order.refunds` ledger row (`UNIQUE (order_id)`, status `pending` / `succeeded` / `failed`, `provider_reference`, `failure_reason`) is inserted *before* the provider call and updated after it; the refund is emitted as the same `order.status.updated` shape (`from`/`to`) as every other status change | The endpoint only flipped DB rows, never moved money, and could not say where a refund went or retry one; and `order.refunded` gave the status family two vocabularies | Refund columns on `payments` (no room for retries/history); provider-call-without-a-row (money moves with no ledger entry); a separate `order.refunded` event type |
| 16 | Producer transport | 2026-10-30 | Request handlers write a row to `<schema>.outbox` in the **same transaction** as the domain change, storing the finished envelope; a relay publishes it afterwards. `NoopEventBus` and every fire-and-forget publish are deleted | A publish after `COMMIT` loses the event on a crash between the two, and a publish before it announces a fact that may roll back. Storing the envelope means the relay re-derives nothing and the contract check fires while the write can still be aborted | Publish-after-commit; an in-process bus with no persistence; storing a bare payload and building the envelope at publish time |
| 17 | Relay placement | 2026-10-30 | One shared **`@ecom/messaging`** package owns the envelope builder, the Postgres store, the relay, and the Kafka publisher; services import `createOutboxModule(options)` from `./nest`. Its core entry has no framework dependency | The claim SQL, the lease, and the retry ladder are exactly the code that gets a bug, and a per-service copy means fixing it N times; the framework-free entry keeps the package's 21 unit tests free of a DI container | Copy `order-svc`'s `outbox/` into each service; `@nestjs/common` in the package's main entry; one shared `messaging.outbox` table across services |
| 18 | Claim and ordering | 2026-10-30 | `FOR UPDATE SKIP LOCKED` + a `locked_until` lease for crash recovery, plus one session advisory lock per schema so only one relay publishes at a time; `for` + `await`, never `Promise.all`; the Kafka message key is the aggregate id | `SKIP LOCKED` stops two workers taking one row but says nothing about order; the advisory lock is what preserves per-aggregate order across a multi-replica deployment, and sequential publish is the reason the key exists. Accepted cost: relay throughput is one batch in flight | Relying on a single replica; publishing inside the claiming transaction (a long transaction across network I/O); parallel publish within a batch |
| 19 | Relay failure policy | 2026-10-30 | The publisher **rethrows**; the relay increments `attempts`, records `last_error`, backs off on `locked_until` (`min(2^attempts, 60)s`), and parks the row at `failed` after five attempts (parity with SQS `maxReceiveCount = 5`) | A swallowing publisher is fatal for a relay: it marks a lost message published. Five attempts matches the queue side, and a parked row is observable instead of retried forever | Fire-and-forget publish; infinite retry; dead-lettering to Kafka at publish time |
| 20 | Packaging | 2026-10-30 | `@ecom/messaging` is **0.1.0**, pre-1.0, distributed as a committed tarball pinned with `file:` exactly like `@ecom/contracts`; `1.0.0` is cut when the third adopter (`ord-011`) lands | Two adopters is not enough evidence to freeze a public surface; the tarball keeps the polyrepo discipline without a registry | `1.0.0` now; a published npm package; a pnpm workspace package shared across repos |
| 21 | One store port, two drivers | 2026-10-31 | `OutboxStorePort<Ctx = Queryable>` with `write(ctx, input)`, implemented by `PostgresOutboxStore` and `MongoOutboxStore`; both feed the same `OutboxRelay`, envelope builder and publisher | The claim SQL, the lease and the retry ladder are the code that gets a bug, and a cms-local relay would duplicate exactly that. The generic keeps the only type safety the seam has (a Mongo session, a `PoolClient`) while leaving the four Postgres call sites source-compatible | A `write(client: unknown)` port; a CMS-specific relay; two packages to version |
| 22 | Mongo claim = repeated atomic `findOneAndUpdate` | 2026-10-31 | The Mongo store claims one document per call, up to `limit`, filtering `status: 'pending'` and `locked_until` null-or-expired, setting a new lease and returning the document after the update | This is the Mongo analogue of `FOR UPDATE SKIP LOCKED`: the filter plus `$set` is atomic per document, so two replicas cannot claim the same row. `find` followed by `updateMany({_id: {$in: …}})` can double-claim between the two round trips | A batch `updateMany` claim; a `findAndModify` with a sort that ignores the lease |
| 23 | Relay lock = lease document, not a mutex insert | 2026-10-31 | Postgres keeps `pg_try_advisory_lock`; Mongo acquires `_id: 'relay'` in `<collection>_locks` with `findOneAndUpdate(..., {upsert: true})` on an expired lease, treats a duplicate-key error as "not acquired", and releases by setting the lease to the epoch | Mongo has no advisory locks. A lease with an expiry makes a crashed relay recoverable automatically; an `insertOne` mutex would leave the lock held forever | `insertOne` as the lock; a lock document with no expiry; no relay lock at all |
| 24 | Quote SQL identifiers | 2026-10-31 | The Postgres store addresses `"<schema>"."<table>"`; the advisory-lock key stays the **unquoted** `schema.outbox` | `order` is a reserved word, so the old `\`${schema}.${table}\`` interpolation made `order.outbox` a syntax error — ord-011 was unreachable without this. Keeping the lock key unquoted preserves the auth and cart lock namespaces, which is what let their suites prove the change was a no-op | Backticking `order` inside order-svc (leaks SQL into a service); a per-service quoting flag |
| 25 | Cache invalidation after commit | 2026-10-31 | A CMS mutation runs document write + revision bump + `cms_outbox` insert in one Mongo session transaction, and calls Redis `del` only after the transaction commits | Redis cannot join a Mongo transaction, so there are exactly two orders. Invalidating first leaves a window where a reader misses the cache, reads the pre-commit document and re-caches it — the write then never becomes visible | Invalidating inside the transaction (false cache-miss window); invalidating before the commit |
| 26 | Decommission the in-process producer bus | 2026-10-31 | catalog's `IEventBus` / `KafkaEventBus` / `InMemoryEventBus` / `EventsService` and cms's `publishCmsUpdated` / `publishBlogUpdated` are deleted. The Kafka **consumer** path and the `media.tasks` publish stay until their own tasks move them | After the outbox cutover nothing publishes through those paths, and a second, unpersisted publish path is exactly the drift the tasks remove. `media.tasks` is not an `EventTopic`, so it cannot ride the relay at all | Keeping the bus "for later"; teaching the relay about transport aliases like `cms.events` |
