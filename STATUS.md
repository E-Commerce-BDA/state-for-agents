**Delivery rules:** at-least-once; manual commit after the side effect and
`processed_events` insert commit together; one consumer group per service
(`postfixId: ''`); five retries with 1/2/4/8/16s backoff, **truncated so the sleeps
fit inside the consumer session** (ADR 44 — the strategy sets `sessionTimeout`
45s/`heartbeatInterval` 3s, and a service may pass `retryBudgetMs`: search-svc passes
20s, which shortens the ladder to 1/2/4/8s); every source topic has
a `.dlq` twin; malformed JSON, invalid known payloads and any error a redelivery
cannot repair (`translateError` — e.g. a `23505` index-constraint violation) go
directly to the DLQ; unknown event types are ignored and committed with a metric.

**Consumer rules:** all three consumers run the same protocol from the package — the service
declares `@EventPattern` routes and a handler, `KafkaEventHandler.run` owns parse → retry ladder →
dead letter → counter → commit, in that order. A failed DLQ write is the **only** throw
(`KafkaConsumerStalledError`) and it is allowed to stop the loop rather than commit past a lost
record. **A ladder that outruns the session is not a retry:** the member is evicted
while it is still sleeping, and `UNKNOWN_MEMBER_ID` then fails the DLQ publish and
the offset commit together, so the group re-joins and replays the same record
forever — which is why the strategy owns `sessionTimeout`/`heartbeatInterval` and the
handler owns `retryBudgetMs` (ADR 44). `search-svc`, `cart-svc` and
`catalog-svc` now run 0.5.0 with a bounded ladder; the earlier live wedge on
`order.created` while this wave was being verified.
`KAFKA_CONSUMER_ENABLED` (default `true`, `false` in the e2e suites) parks a consumer
without touching the API, and a broker that is down retries every 5 s instead of blocking boot.
The Nest strategy appends `-server` to the group id unless `postfixId` is `''`, so
`<service>-server` must never appear in `kafka-consumer-groups --list`.

**Producer rules:** request handlers never publish directly. catalog and order write a Postgres
outbox in the same transaction as the domain change; CMS writes `cms_outbox` in a Mongo
transaction (replica set required). All five producers share one `@ecom/messaging` outbox store
(0.2.0 for four of them, 0.4.0 for cms-svc since `cms-006`; the store signature did not change): the store
validates the envelope and the payload before the insert, the Postgres store quotes its
identifiers and claims with `FOR UPDATE SKIP LOCKED` under one session advisory lock per schema,
the Mongo store claims one document at a time with `findOneAndUpdate` under a lease document,
the relay publishes sequentially keyed by aggregate id, marks published only after the broker
acks, and retries with a `locked_until` backoff before parking at `failed` after five attempts.
There is no second producer path in any service: catalog's `KafkaEventBus`, cms's direct
`cms.events` publish and cms's direct Kafka `media.tasks` publish are all deleted — the last one
replaced by one SQS task per upload (`cms-006`).

**Task rules:** a task is not an event — no topic, no consumer group, no replay. Every task is a
`TaskMessage` (`id`, `queue`, `type`, `idempotencyKey`, `enqueuedAt`, `payload`) validated by
`taskMessageSchema` before the send; the idempotency key is the aggregate id (for media, the media
id), and the worker deletes a message only after the handler resolves, so a failure makes it
visible again. There is no hand-rolled DLQ publisher: the queue's redrive policy
(`maxReceiveCount 5`, provisioned by Terraform and the LocalStack init) owns it, and the worker
logs `ApproximateReceiveCount`. `SQS_TASKS_ENABLED` (default `false` in development) parks the
worker without touching the API.
