**Delivery rules:** at-least-once; manual commit after the side effect and
`processed_events` insert commit together; one consumer group per service
(`postfixId: ''`); five retries with 1/2/4/8/16s backoff; every source topic has
a `.dlq` twin; malformed JSON and invalid known payloads go directly to the
DLQ; unknown event types are ignored and committed with a metric.

**Producer rules:** request handlers never publish directly. catalog and order write a Postgres
outbox in the same transaction as the domain change; CMS writes `cms_outbox` in a Mongo
transaction (replica set required). All five producers share `@ecom/messaging` 0.2.0: the store
validates the envelope and the payload before the insert, the Postgres store quotes its
identifiers and claims with `FOR UPDATE SKIP LOCKED` under one session advisory lock per schema,
the Mongo store claims one document at a time with `findOneAndUpdate` under a lease document,
the relay publishes sequentially keyed by aggregate id, marks published only after the broker
acks, and retries with a `locked_until` backoff before parking at `failed` after five attempts.
There is no second producer path in any service: catalog's `KafkaEventBus` and cms's direct
`cms.events` publish are deleted.
